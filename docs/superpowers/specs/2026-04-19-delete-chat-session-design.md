# 删除对话功能设计

- 日期：2026-04-19
- 主题：聊天侧栏删除对话

## 背景

当前聊天侧栏支持创建与切换会话，但缺少删除能力。随着会话增加，用户无法清理旧对话，侧栏会越来越拥挤，影响日常使用。

## 目标

为聊天侧栏增加单条“删除对话”能力，满足以下目标：

1. 用户可以从侧栏对任意单条会话发起删除
2. 删除前必须二次确认，并明确提示“删除后不可恢复”
3. 删除当前会话后，界面跳转到新的空白学习态
4. 删除非当前会话时，仅刷新侧栏列表，不打断当前对话
5. 保持现有页面结构与风格，采用最小改动实现

## 非目标

本次不包含以下内容：

- 批量删除
- 删除撤销
- 会话重命名
- 会话归档
- 多操作菜单扩展

## 用户交互设计

### 侧栏入口

在每条会话卡片右上角增加“更多”按钮。用户点击后展开轻量菜单，当前版本仅包含一项：`删除对话`。

之所以采用“更多菜单”而不是常显删除按钮，是因为侧栏宽度有限，且删除属于低频高风险操作。菜单入口可以减少误触，并保持会话列表视觉整洁。

### 删除确认

用户点击“删除对话”后，弹出确认交互，文案需要明确表达不可恢复性，例如：

- 标题：删除对话
- 内容：删除后不可恢复，确认删除这个对话吗？
- 操作：取消 / 删除

本次优先使用最轻量的确认实现，避免为一个单功能需求引入复杂弹窗系统。

### 删除后的页面行为

#### 删除非当前会话

- 关闭确认框
- 调用删除接口
- 成功后从侧栏列表中移除该项
- 保持当前页面与当前会话不变

#### 删除当前会话

- 关闭确认框
- 调用删除接口
- 成功后从侧栏列表中移除该项
- 跳转到聊天空白态，让用户可以立即开始新的学习会话

### 错误反馈

删除失败时，在侧栏区域显示中文错误提示，例如“删除会话失败，请稍后重试”。错误反馈应短小直接，不影响其他会话项交互。

## 技术设计

### 前端改动

#### 1. API 封装

在 `frontend/src/lib/api.ts` 新增 `deleteSession(sessionId: number)`：

- 请求方法：`DELETE`
- 地址：`/api/chat/sessions/{session_id}`
- 携带现有认证头
- 删除失败时返回统一中文错误

#### 2. 侧栏组件状态

在 `frontend/src/components/chat/SessionSidebar.tsx` 内扩展以下状态：

- 当前打开菜单的会话 ID
- 待删除会话信息
- 删除中状态
- 删除错误提示

侧栏仍保持当前“本地维护 sessions 列表”的方式，不引入额外全局状态管理。

#### 3. 菜单与确认交互

在会话项右上角增加“更多”触发器。点击后展示菜单，点击“删除对话”进入确认流程。

确认通过后：

- 调用 `deleteSession`
- 本地移除对应会话
- 清理菜单和待删除状态
- 若删除项为当前会话，则执行路由跳转

#### 4. 跳转策略

当前项目聊天路由为 `/chat/[sessionId]`。删除当前会话后，前端应创建一个新的空会话，并在删除成功后直接跳转到该新会话对应的聊天页，以展示空白新学习态。

之所以不跳转到 `/`，是因为当前首页会自动跳到已有会话；在存在其他历史会话时，这会把用户带回旧会话，而不是用户期望的“新学习会话”空白态。因此本次应复用现有创建会话接口，在前端完成“删除当前会话 → 创建新会话 → 跳转到新会话”的顺序流程。

### 后端改动

#### 1. 新增删除接口

在 `backend/app/api/chat.py` 新增：

- `DELETE /api/chat/sessions/{session_id}`

行为约束：

- 仅允许删除当前登录用户自己的会话
- 会话不存在时返回 404
- 删除成功返回简单成功响应，例如 `{ "success": true }`

#### 2. 服务层删除方法

在 `ChatService` 中新增删除方法，例如 `delete_session(session_id: int, user_id: int)`：

- 先校验该会话属于当前用户
- 再执行删除与提交
- 不允许跨用户删除

#### 3. 级联删除依赖

当前 `ChatSession` 模型中的 `messages` 与 `resources` 已配置 `cascade="all, delete-orphan"`，因此删除会话时，关联聊天消息与生成资源会一起删除，无需额外单独清理逻辑。

## 数据流

1. 用户点击某条会话右上角“更多”按钮
2. 用户点击“删除对话”
3. 前端弹出确认
4. 用户确认删除
5. 前端调用 `DELETE /api/chat/sessions/{session_id}`
6. 后端校验用户归属并删除会话
7. 前端根据结果更新侧栏列表
8. 若删除的是当前会话，则跳转到空白新学习态

## 边界与异常处理

### 会话不存在

如果目标会话已被删除或不存在：

- 后端返回 404
- 前端提示删除失败
- 可选择同步刷新列表，或在当前实现中先保守仅提示错误

### 重复点击

删除确认后的提交按钮应在请求期间禁用，避免重复触发删除请求。

### 当前菜单与路由变化

如果用户在菜单打开时切换了路由或列表发生变化，组件应在删除成功或取消后清空菜单状态，避免遗留悬浮菜单。

## 测试与验证

至少验证以下场景：

1. 删除非当前会话，列表即时移除
2. 删除当前会话，成功跳到空白新学习态
3. 删除后刷新页面，列表状态仍正确
4. 未登录或越权删除时，接口不能删除他人会话
5. 构建通过，前端无类型错误

## 方案对比结论

### 方案一：侧栏更多菜单 + 删除确认（推荐）

优点：

- 与现有侧栏信息密度匹配
- 误触风险低
- 交互清晰
- 改动范围小

缺点：

- 比直接显示删除按钮多一次点击

### 方案二：仅当前会话提供删除按钮

优点：

- 实现简单

缺点：

- 无法在列表层面管理历史会话
- 不满足从侧栏清理旧会话的目标

### 方案三：侧栏编辑态 / 批量删除

优点：

- 扩展空间更大

缺点：

- 明显超出当前需求
- 会带来更多状态与交互复杂度

因此本次采用方案一。

## 实施建议

本功能应按“后端删除接口 → 前端 API 封装 → 侧栏菜单与确认交互 → 跳转与错误处理 → 验证”的顺序实施，以便每一步都能独立验证。
