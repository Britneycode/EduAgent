# 比赛版 Tutor 驱动学习闭环设计

- 日期：2026-04-20
- 主题：以 Tutor 为主线整合资源生成、路径动态调整、效果评估与比赛稳定性能力

## 背景

当前项目已经具备聊天页、资源卡片、基础学习路径页以及 Media Agent 的初版能力，但整体仍偏“分散功能”：

- `MediaAgent` 目前仅覆盖思维导图与 PPT 大纲生成
- `PlannerAgent` 仍是简单的资源类型返回，尚未形成真正的多 Agent 闭环编排
- 学习路径页仍以前端根据 prerequisites 拼接路径为主，缺少基于学习反馈的动态调整
- 聊天页可以展示资源卡片，但缺少路径更新、效果评估、资源联动等统一学习回合视图
- 审核、缓存、可观测、演示数据等能力尚未围绕“比赛演示稳定性”收敛

本轮目标不是同时把所有能力都做成生产级，而是围绕比赛演示场景，设计一条“看得见、讲得清、跑得稳”的学习闭环主线。

## 目标

本次设计聚焦“可演示的比赛版本”，目标如下：

1. 以 Tutor 为主导输出，形成“讲解 → 资源 → 评估 → 路径调整 → 下一步建议”的完整学习闭环
2. 让多 Agent 协同在一轮对话中可感知、可展示，而不是分散在多个页面中
3. 将 Media Agent 聚焦到比赛最直观、最稳定的多模态输出形式
4. 让学习路径支持基于答题结果和对话反馈的动态调整
5. 补足效果评估、轻量缓存、降级策略、可观测与演示数据，以提高现场演示稳定性

## 非目标

本次不包含以下内容：

- 生产级完整多媒体链路（如视频生成、真实动画渲染、完整 PPT 文件导出）
- 长周期学习画像建模与复杂趋势分析
- 复杂审核工作流、多级缓存体系、完整监控平台接入
- 独立的资源推荐引擎或召回排序系统
- 面向多课程、多租户的通用平台化改造

## 演示主线设计

本轮比赛版选择“Tutor 边辅导边联动资源与路径，形成完整学习闭环”作为统一主线。

用户提出学习目标后，系统识别为“辅导 + 资源 + 路径”复合请求，由 Router 判定、Planner 编排，随后由 Tutor 作为主讲 Agent 输出主回答，同时调度所需资源生成、路径更新与评估模块。前端聊天页持续流式展示以下结果：

1. Tutor 对目标知识点的即时讲解
2. 与当前讲解强相关的资源卡片（思维导图、算法图解、题目等）
3. 根据答题结果与对话反馈得出的评估摘要
4. 根据评估结果重新调整的学习路径摘要
5. 明确的下一步建议

这样一轮响应中即可同时体现：

- 多 Agent 协同
- 画像驱动
- 资源生成
- 动态路径调整
- 学习效果评估

相比单独展示资源生成或单独展示学习路径，这条主线更像一个完整产品，更适合比赛答辩与现场演示。

## 设计决策

### 1. Tutor 风格：混合型

本轮 Tutor 采用“混合型”主导风格：先快速响应，再根据用户反馈动态加深与调整。

采用该方案的原因：

- 纯结果型虽然节奏快，但个性化感较弱
- 纯引导式虽然更像老师，但比赛演示前置对话过多，容易拖慢节奏
- 混合型可以兼顾“快速展示能力”和“展示动态适配”两个目标

具体表现为：

- 第一轮先给出可见结果，证明系统能快速理解并产出内容
- 后续通过答题和追问展示系统如何更新画像、调整路径、切换资源深度

### 2. Media Agent 范围：思维导图 + 算法图解/流程图

本轮 Media Agent 不追求重媒体产物，而聚焦两种即时可展示内容：

- 思维导图
- 算法图解 / 流程图

不将完整 PPT 文件、动画视频、音视频链路作为比赛版主输出，原因如下：

- 这些能力链路更长，失败点更多
- 即时嵌入聊天流的视觉效果不如图解直接
- 比赛演示更需要稳定、清晰、可嵌入式的结果

因此，Media Agent 的比赛版目标是输出可直接在聊天流和资源中心展示的 Mermaid / SVG / Markdown 图解内容，而不是重文件下载型产物。

### 3. 路径动态调整触发：答题结果 + 对话反馈混合驱动

学习路径的调整信号采用混合触发：

- 答题结果，如正确率、错误知识点、题目完成情况
- 对话反馈，如“没听懂”“太简单”“想深入一些”

该方案比单纯看做题结果更灵活，也比单纯看自然语言反馈更稳定，最适合演示系统“真的理解用户当前状态并做出调整”。

### 4. 效果评估粒度：中等版

本轮效果评估选择中等粒度，输出以下维度：

- 知识点掌握度变化
- 当前薄弱点
- 学习节奏建议

不在本轮纳入认知风格长期趋势、资源偏好演化、长期多轮成长曲线等更重能力。这样既能展示动态画像更新，又不会让实现和演示过重。

## 整体架构设计

比赛版不将五个待完善方向拆成彼此独立的大模块，而是围绕“比赛版 Tutor 驱动学习闭环”组织一层统一编排。

整体上，系统分为四个层次：

1. **Router / Planner 编排层**
   - Router 识别用户意图
   - Planner 为复合学习请求选择比赛版闭环流程

2. **学习回合执行层**
   - Tutor：主讲解与主节奏控制
   - Quiz / Media / Path / Evaluation：按需生成辅助结果

3. **共享知识与画像层**
   - LLM Wiki：为 Tutor 与 Media 等模块提供知识上下文
   - 学生画像：为资源深度、路径建议、评估更新提供个性化依据

4. **前端展示层**
   - 聊天页：本轮学习闭环的主舞台
   - 资源中心与路径页：承接详情查看与历史复盘

### 核心原则

- Tutor 必须始终是主输出，避免前端被多个平级 Agent 输出打散
- 资源、路径、评估都挂在同一轮学习回合之下
- 路径页和资源中心不再承担“主流程入口”，而改为主流程的详情扩展页
- 任何增强项失败时，都不能阻塞 Tutor 主回答

## 模块职责拆分

### Tutor Agent：主讲人

Tutor Agent 在比赛版中的职责从“单独答疑”升级为“学习回合主持人”。它负责：

- 组织 Tutor 主回答
- 汇总其他模块的结果并自然融入对话
- 决定当前回合的节奏是“解释”“练习”“复盘”还是“推进下一步”
- 输出下一步建议

Tutor 不直接承担所有子任务的计算，但它是前端感知到的“主声音”。

### Media Agent：即时可展示的图解生成器

Media Agent 在现有基础上保留 `mindmap`，同时新增或强化“算法图解 / 流程图”输出能力。

比赛版要求：

- 优先输出 Mermaid、结构化 Markdown 图解、可转 SVG 的图形描述
- 输出结果必须适合聊天流即时展示
- 图解内容应与 Tutor 当前讲解主题保持强绑定

### Path Service：轻量动态路径服务

路径服务从“静态 prerequisites 列表”升级为“可调整的学习路径摘要”。

比赛版路径输出不追求复杂 DAG 可视化编辑，而是提供：

- 当前目标知识点
- 推荐前置知识列表
- 已掌握 / 待巩固 / 下一步 三类节点分组
- 当前优先推进建议

路径服务的更新依据来自评估结果和对话反馈。

### Evaluation Service：轻量效果评估模块

新增独立的效果评估模块，输入为：

- Quiz 结果
- 用户自然语言反馈
- 当前主题与画像上下文

输出为：

- 掌握度变化摘要
- 当前薄弱点
- 节奏建议
- 是否需要调整路径或资源类型

该模块会驱动画像更新，但比赛版只更新本轮需要展示的中等粒度字段。

### 前端学习回合展示层

前端聊天页从“消息列表 + 资源数组”升级为“学习回合视图”。

一轮 assistant 响应中应至少包含：

- Tutor 主回答
- 资源卡片组
- 路径调整卡
- 评估摘要卡
- 下一步行动建议

这样用户在一个地方就能看到系统如何协同工作，避免必须跳转多个页面才能理解流程。

## 数据流设计

比赛版闭环中的一次典型数据流如下：

1. 用户发送学习请求
2. Router 识别为复合学习意图
3. Planner 进入比赛版学习闭环流程
4. Tutor 基于 Wiki 和画像生成主讲解
5. Planner 按当前回合需求触发 Media / Quiz / Path / Evaluation
6. 资源生成结果通过 SSE 流式下发
7. 若用户完成题目或给出反馈，则 Evaluation 计算掌握度变化与薄弱点
8. Path Service 根据评估结果输出路径调整摘要
9. Tutor 汇总当前结果，给出下一步建议
10. 前端将本轮结果挂在同一学习回合下展示

## 核心数据结构设计

比赛版新增统一的“学习回合结果”概念，避免前端继续自行猜测哪些数据属于哪一轮。

建议引入如下结构：

```ts
interface LearningTurnResult {
  tutor_response: string;
  resources: ResourceCard[];
  path_update?: PathUpdate;
  evaluation?: EvaluationSummary;
  profile_delta?: ProfileDelta;
  next_actions: string[];
}
```

建议各字段职责如下：

- `tutor_response`：Tutor 主回答文本
- `resources`：本轮资源卡片数组
- `path_update`：当前回合路径动态调整摘要
- `evaluation`：学习效果评估摘要
- `profile_delta`：本轮画像变化概览
- `next_actions`：下一步建议，如先看图解、先做题、继续深入

### 资源类型调整

现有 `ResourceType` 建议补充专门的图解类型，例如 `diagram`，用于承载算法图解 / 流程图。

不建议继续把所有结构化图形都塞进 `mindmap`，否则：

- 语义不清晰
- 前端展示策略难以区分
- 资源中心无法做精确筛选与联动

## 前后端接口设计

### 聊天流接口

聊天 SSE 流需要从“token + resource_card”升级为支持学习闭环事件。

建议新增事件：

- `path_update`：当前回合路径调整结果
- `evaluation_update`：当前回合评估结果
- `profile_delta`：当前回合画像变化摘要
- `next_actions`：当前回合下一步建议

这样聊天页可以边接收 Tutor 流式文本，边插入路径与评估卡片，形成演示效果更强的实时编排感。

### 路径接口

路径接口不再只返回 prerequisites 列表，而改为返回带分组状态的路径节点集合，例如：

- 已掌握
- 待巩固
- 下一步
- 目标知识点

这样路径页既能复用比赛版闭环结果，也能独立展示路径详情。

### 资源接口

资源接口保持现有中心化查询思路，但需要兼容新的 `diagram` 类型，并支持资源与知识点、路径节点之间的关联字段，方便后续联动展示。

## 资源展示与联动设计

聊天页中的资源展示不再只是简单按生成顺序堆叠，而是强调“与当前学习回合同步”。

### 聊天页中的资源联动

- Tutor 当前讲的是哪个知识点，资源卡片就优先挂载该知识点对应内容
- 路径卡中的“下一步节点”应能映射到资源卡片
- 评估卡中发现的薄弱点应关联到补强资源推荐

### 资源中心中的延伸展示

资源中心继续承担沉淀与回看职责，但比赛版优先支持以下能力：

- 按资源类型过滤
- 显示关联知识点
- 显示来源 Agent
- 支持从聊天页进入资源详情

不在本轮加入复杂收藏、标签编辑、跨资源图谱导航等更重能力。

## 错误处理与降级策略

比赛版的最高原则是：任何增强模块波动，都不能把整轮演示拖垮。

因此编排策略采用“**Tutor 必达，其他模块尽力而为**”。

### 降级规则

- **Tutor 失败**：整轮失败，返回统一中文错误提示
- **Media 失败**：保留 Tutor 文字讲解，提示本次未生成图解
- **Quiz / Evaluation 失败**：保留讲解与路径，不展示评估卡
- **Path 失败**：保留讲解与资源，回退为文字版“下一步建议”
- **Wiki 检索不足**：允许 Tutor 继续回答，但需通过既有机制标注为通用补充说明

### 设计原因

- 演示现场最重要的是连续性
- 观众首先看到的是“系统是否能一直回应”，而不是某个增强能力是否百分百命中
- 将增强模块设计为可选降级项，可以显著提升比赛稳定性

## 审核、缓存与可观测设计

### 内容审核

比赛版采用统一输出后审核，而不是在每个 Agent 中间步骤引入审核流程。

理由：

- 中间步骤审核会拉长链路
- 会增加更多失败点
- 比赛版更需要稳定和可预测的输出时间

因此本轮仅在最终要展示给用户的文本和图解描述上做统一审核。

### 轻量缓存

缓存策略以“相同主题 + 相近画像 + 相同资源类型”的最近结果复用为主，优先覆盖：

- 思维导图
- 算法图解 / 流程图
- 题目

这些内容生成成本相对较高，且在比赛场景中复用价值高。

本轮不引入复杂多级缓存和缓存一致性策略。

### 可观测性

比赛版只做最小但足够展示的可观测能力，记录：

- 本轮触发了哪些 Agent / 服务
- 各模块耗时
- 是否命中缓存
- 是否发生降级
- 最终学习回合是否成功完成

这些信息既可用于日志排障，也适合在演示时辅助说明系统确实存在协同编排。

## 演示数据设计

为保证比赛现场稳定复现，建议预置少量典型学生画像与主题案例，例如：

- 基础薄弱型学生
- 偏代码实战型学生
- 竞赛冲刺型学生

每种画像都配套典型学习主题和预期路径变化，方便在演示时快速触发不同效果。

这类数据不属于生产能力的一部分，但对于比赛版非常重要，因为它可以帮助系统稳定地表现出“个性化差异”。

## 测试与验证

比赛版测试重点围绕演示主线，而不是面面俱到。

### 后端验证

- Planner 是否能产出比赛版学习回合结构
- Evaluation 是否能根据答题和反馈输出掌握度变化、薄弱点、节奏建议
- Path Service 是否能输出分组后的路径摘要
- Media Agent 是否能稳定输出思维导图与图解资源

### 前端验证

- 聊天页能否展示 Tutor 主回答、资源卡、路径卡、评估卡
- SSE 事件是否能正确驱动学习回合更新
- 降级场景下 UI 是否能正常回退

### 端到端验证

至少覆盖以下完整故事线：

1. 用户提出学习目标
2. Tutor 给出讲解
3. 系统生成图解与题目
4. 用户反馈“没听懂”或做错题
5. 系统更新评估摘要并调整路径
6. Tutor 给出新的下一步建议

### 降级验证

至少验证以下场景：

- Media 不可用时，闭环仍可完成
- Path 更新失败时，Tutor 仍能继续引导
- Evaluation 缺失时，不会阻塞资源展示

## 分阶段实施建议

建议按以下顺序推进，保证每一步都可以独立验收并支持演示：

### 第一阶段：闭环输出骨架

- 定义学习回合结果结构
- 打通聊天页的 Tutor 主回答 + 路径区 + 评估区 + 资源区展示骨架
- 保证空状态、加载状态、降级状态都能正确展示

### 第二阶段：路径与评估闭环

- 新增轻量 Evaluation Service
- 让路径接口返回带状态分组的节点
- 打通答题结果 + 对话反馈驱动的动态调整

### 第三阶段：Media Agent 增强

- 保留思维导图
- 增加算法图解 / 流程图资源类型与生成链路
- 接入聊天页与资源中心展示

### 第四阶段：资源联动与推荐

- 让资源卡片与路径节点建立关联
- 让评估摘要支持推荐补强资源
- 优化聊天页中“从解释到行动”的引导体验

### 第五阶段：比赛稳定性增强

- 增加轻量缓存
- 增加降级日志与可观测字段
- 补充演示画像与示例数据
- 补统一输出审核

## 方案结论

本次采用“**Tutor 驱动的比赛版学习闭环**”作为统一设计方案，而不是分别孤立推进 Media、路径、资源展示、审核缓存、可观测等子方向。

该方案的核心优势在于：

- 最适合比赛讲故事
- 亮点集中，能够同时体现多 Agent、画像、资源、路径与评估
- 改造范围相对可控
- 易于做降级和稳定性保障

其代价是：

- 审核、缓存、可观测只做到比赛可用版本
- 部分平台化能力需要后续继续深化

但这与本轮“可演示的比赛版本”目标完全一致，因此是当前最合适的推进方案。
