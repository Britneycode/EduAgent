# EduAgent 路线图与比赛演示版实施设计

日期：2026-04-16
主题：EduAgent 全项目路线图拆解与比赛演示版实施方案

## 1. 背景与目标

当前仓库已经具备部分后端骨架与设计文档，但距离 `PLAN.md` 中定义的完整 EduAgent 仍有较大差距。项目目标不是单一功能开发，而是围绕高校学习场景，构建一个以 LLM Wiki 为知识中枢、具备多 Agent 协同、画像驱动、资源生成、学习路径和智能辅导能力的比赛级产品。

本次设计不直接追求“一次做完整个系统”，而是先把全项目拆成可落地的路线图，再确定首个可交付版本的范围、顺序和边界，确保：

- 能尽快产出比赛可演示版本
- 不因为短期演示牺牲后续可扩展性
- 尽量复用当前已有代码骨架，避免推倒重来

本次已确认的关键方向：

1. 先拆路线图，再从 Phase 1 开始落地
2. 总体策略采用“折中方案”
3. 前后端一起推进
4. 真实集成优先
5. 首个可交付版本定位为“比赛演示版”
6. 工程增强项允许延后

## 2. 推荐实施方案

本次评估了三种路线：

### 方案 A：比赛 MVP 分阶段闭环（推荐）
按阶段逐步打通能力，每一阶段都形成一个真实可运行、可演示、可验收的闭环。

- Phase 1：最小 Wiki + 最小画像基线 + 聊天与 3 类资源生成闭环
- Phase 2：完整 Wiki / RAG / 画像闭环 + 知识图谱 / DAG 前置能力
- Phase 3：比赛演示版核心功能闭环（路径 / Tutor / 资源中心 / Wiki 浏览）
- Phase 4：增强与打磨

**优点**
- 最符合“比赛可演示 + 后续可继续迭代”的目标
- 能较早产出稳定 Demo
- 与现有代码结构兼容度最高

**缺点**
- 前几阶段会有“先够用、后增强”的取舍
- 需要明确哪些能力是首版必须真实可用，哪些延后

### 方案 B：后端能力先完整，前端后补
优先把 Wiki、画像、Agent 编排、路径、Tutor 等 API 和数据流全部做稳，再统一完善前端。

**优点**
- 架构更整齐
- 后续联调更顺

**缺点**
- 前期不容易形成比赛可见成果
- 用户侧感知慢

### 方案 C：前端演示先行，后端按页面倒推
优先把聊天页、画像页、路径页、Wiki 页做成可演示 UI，再逐步替换为真实后端。

**优点**
- 界面见效快
- 适合极短期展示

**缺点**
- 容易积累假数据与返工
- 不符合“真实集成优先”

### 方案结论
推荐采用 **方案 A：比赛 MVP 分阶段闭环**。后续实现围绕“先形成可见价值，再扩下一条链路”的原则推进。

## 3. 总体路线图

建议把整个项目拆成 4 个可交付里程碑，每个里程碑都必须达到“可运行、可演示、可验收”。

### 里程碑 1：最小知识支撑下的聊天与资源生成闭环
目标：用户可以发起聊天请求，并通过 SSE 流式获得至少 3 类学习资源；首版生成链路不允许完全脱离知识库上下文。

包含内容：
- 会话创建、消息保存、资源保存
- RouterAgent / PlannerAgent 主链路可用
- 最小 Wiki 可用：完成初始知识库导入、基础检索接口与生成前检索接入
- 最小画像基线可用：能创建基础画像记录，并把显式用户背景带入资源生成
- DocAgent / QuizAgent / CodeAgent 真实生成
- 聊天页、流式消息渲染、Agent 状态展示、资源卡片展示

### 里程碑 2：完整知识中枢与画像闭环
目标：系统真正具备“Wiki 支撑 + 画像驱动”的 EduAgent 核心特征，并为后续学习路径生成补齐知识图谱 / DAG 前置能力。

包含内容：
- 完整知识导入、向量索引与基础 BM25 / 向量混合检索
- 知识图谱 / DAG 基础结构可查询，能支撑后续路径规划
- Agent 生成前强制检索 Wiki
- 引用信息回传前端
- ProfileAgent 画像提取、更新与持久化
- 画像页与引用展示

### 里程碑 3：比赛演示版核心功能闭环
目标：达到首个可交付版本——比赛演示版，并确保演示主线可在一次完整流程中稳定走通。

包含内容：
- 学习路径生成与展示
- TutorAgent 问答
- 资源中心与资源详情
- Wiki 浏览页
- 更完整的 Agent 状态与资源组织展示
- 演示脚本所需的中文页面文案与关键空态 / 异常态提示

### 里程碑 4：增强与打磨
目标：在不破坏主链路的前提下增强稳定性、表现力和交付质量。

包含内容：
- MediaAgent
- 输出审核
- 缓存与性能优化
- 失败恢复与日志
- Demo 打磨与提交材料支持

## 4. 各里程碑的范围边界与取舍

### 4.1 里程碑 1：最小知识支撑下的聊天与资源生成闭环
**必须做**
- 后端：聊天会话、消息保存、`/api/chat/stream` SSE、Router、Planner、Doc / Quiz / Code
- 前端：聊天页面、流式消息、资源卡片、Agent 状态
- 数据：资源落库、会话回看
- 最小 Wiki：只覆盖 1 个演示课程主题；数据最小颗粒度统一为“wiki 条目”，每条至少包含 `title`、`content`、`source_chapter`；基础检索输入只接受 `topic` 文本，返回最少 1 条命中条目或空结果
- 最小画像基线：首版字段集固定为 `grade_level`、`goal`、`skill_level`、`preferred_style`；来源仅限用户在当前会话中的显式输入；首版全部字段均可为空，不做自动推理补全；若为空，则生成链路按默认通用模式执行

**暂不做**
- 复杂权限体系
- 多媒体生成
- 学习路径规划
- 高级画像推理
- 高级召回、Rerank 优化

**原因**
这是最短可见路径，能最快把当前聊天 API 和 Orchestrator 主链路做成稳定 Demo，同时避免首版在 Wiki 和画像上过度扩张。

### 4.2 里程碑 2：知识中枢与画像闭环
**必须做**
- Wiki 知识导入
- 向量索引与检索
- 生成前强制检索知识上下文
- ProfileAgent 画像更新
- 画像持久化与画像页展示
- 前端显示知识引用信息

**暂不做**
- 复杂知识图谱前端
- 高级召回、Rerank 优化
- 高阶行为建模
- 画像自动纠偏

**原因**
该阶段完成后，系统才真正具备“知识中枢 + 个性化”的比赛差异化。

### 4.3 里程碑 3：比赛演示版核心功能闭环
**必须做**
- 学习路径 API 与路径页
- TutorAgent
- 资源中心与资源详情
- Wiki 浏览页
- 聊天页更完整的 Agent 状态与结果编排展示

**取舍策略**
- 路径规划首版采用规则 + DAG + 画像过滤，不做复杂自适应优化
- 路径生成输入边界固定为：用户当前显式目标、当前画像摘要、Wiki 知识图谱 / DAG 关系；首版不读取学习行为日志，不依赖长期历史建模
- 路径生成在输入缺失时的规则固定为：缺目标时返回通用入门路径；缺画像时按通用学生画像生成；缺 DAG 时不生成正式路径结果，而返回中文受控提示
- 路径输出最小结构固定为：路径标题、适用目标、节点列表；每个节点至少包含 `title`、`description`、`wiki_entry_ref`、`order`
- Tutor 聚焦基于 Wiki 与当前会话资源的高质量答疑，不做长期教学记忆
- 资源中心首版只做列表与详情，不做复杂筛选、批量操作与协作能力
- Wiki 页先做浏览、检索、详情，不做协作编辑后台
- 比赛演示版以“单条主线稳定走通”为目标，不要求所有页面都达到产品化完善程度

**原因**
该阶段目标不是补齐完整产品，而是把多 Agent、画像、资源生成、路径、答疑、知识中枢等比赛展示主线稳定串成一次可重复演示流程。

### 4.4 里程碑 4：增强与打磨
**放到这一阶段的内容**
- MediaAgent：PPT / 视频 / 动画
- 内容安全审核
- 缓存优化
- 更细的失败恢复
- 资源回写 Wiki 的审核流
- 可观测性与性能调优

**原因**
这些内容主要提升稳定性、自动化和展示效果，不应阻塞比赛演示版主链路。

## 5. 推荐代码落地架构

结合当前代码状态：

- 后端已经有应用入口与生命周期初始化：`backend/app/main.py`
- 聊天流式接口已有基础实现：`backend/app/api/chat.py`
- 编排器已经能串起 Profile / Doc / Quiz / Code：`backend/app/agents/orchestrator.py`
- 前端目前仍较薄，仅具备 Next.js 基础骨架与少量依赖：`frontend/package.json`

因此建议采用：**后端在现有骨架上补齐，前端按比赛 Demo 路径反推页面与组件结构。**

### 5.1 后端落地架构

#### API 层保持薄
API 层只负责：
- 参数校验
- 认证挂载
- 调用 service / orchestrator
- 返回 SSE 或 JSON

主接口建议收敛为：
- `/api/chat/session`
- `/api/chat/stream`
- `/api/profile`
- `/api/resources`
- `/api/path`
- `/api/wiki`

接口职责进一步约束如下：
- `/api/chat/stream`：只负责接收用户消息、保存 user message、创建 orchestrator、透传事件流
- `/api/profile`：只负责读取当前画像与画像摘要，不承担聊天链路中的画像提取
- `/api/resources`：只负责资源列表、资源详情、按会话或类型过滤查询
- `/api/path`：只负责路径生成结果读取与触发，不直接承担 Tutor 或资源生成逻辑
- `/api/wiki`：只负责知识条目浏览、检索、详情与引用来源查询

#### Orchestrator 只做编排
后续不建议继续把数据库写入、复杂回退、引用整理和查询逻辑继续堆进 Orchestrator。建议边界为：
- `Orchestrator`：接收请求上下文、调度 Agent、发事件流、聚合本轮 assistant 输出
- `ChatService`：会话创建、消息落库、会话历史查询
- `ResourceService`：资源落库、资源列表、资源详情查询
- `ProfileService`：画像持久化、画像摘要读取
- `PathService`：路径结果持久化与查询
- `WikiService`：知识检索、引用组织、知识图谱 / DAG 查询

落地约束：
- Orchestrator 可以在流结束时触发 message / resource 持久化，但不直接承载列表查询与详情查询逻辑
- Agent 不直接操作数据库表，所有持久化统一经由 service 层
- 前端页面只依赖 API 返回的数据契约，不直接感知 Agent 内部实现细节

#### Agent 边界明确
建议分三类：

**编排类**
- `RouterAgent`
- `PlannerAgent`

**生成类**
- `DocAgent`
- `QuizAgent`
- `CodeAgent`
- `TutorAgent`
- `MediaAgent`

**上下文类**
- `ProfileAgent`

核心规则：
- Router 只判断意图
- Planner 只决定调哪些 Agent 和顺序
- 各生成 Agent 必须通过 Wiki 获取知识上下文
- Profile 只负责画像提取与更新

#### Wiki 作为生成前置依赖
在“真实集成优先”前提下，Wiki 不应是可选增强，而应是生成链路的前置步骤：
- Doc / Quiz / Code / Tutor 在生成前先检索 Wiki
- 结果返回最小引用信息
- 前端资源卡片支持显示来源章节 / 来源条目
- 检索失败时进行受控降级，而不是默认裸生成

受控降级规则建议统一为：
- Phase 1：若 Wiki 服务可用但当前 topic 未命中内容，允许生成 Agent 基于显式 topic 与最小画像基线继续生成，同时前端明确提示“当前知识库未命中，结果未附带知识引用”
- Phase 1：若 Wiki 服务整体不可用，则本轮资源生成直接返回中文错误提示，不进入静默裸生成
- Phase 2 及之后：Doc / Quiz / Code / Tutor 默认要求先完成 Wiki 检索；若检索链路异常，只允许返回受控错误或显式降级说明，不允许前端误以为结果具备知识依据
- 所有降级结果都必须在 SSE 事件或最终页面状态中给出清晰中文提示

### 5.2 前端落地架构

#### 页面顺序按比赛演示链路安排
优先顺序建议为：
1. 聊天页 `chat/[sessionId]`
2. 资源中心 `resources`
3. 画像页 `profile`
4. 路径页 `path`
5. Wiki 页 `wiki`

#### 组件结构按“容器 + 资源类型组件”组织
聊天页建议拆分为：
- `ChatShell`
- `SessionSidebar`
- `MessageList`
- `Composer`
- `AgentStatusPanel`
- `ResourceCard`

资源卡片进一步按类型细分：
- `DocumentCard`
- `QuizCard`
- `CodeCard`
- 后续扩展 `MindmapCard` / `PathCard`

#### 前端数据层做最小封装
建议补齐：
- `lib/api.ts`：REST 请求
- `lib/sse.ts`：SSE 事件解析
- `lib/types.ts`：前端类型映射
- `lib/store.ts`：聊天与流式状态

首版状态管理只聚焦：
- 当前会话
- 流式 token
- Agent 状态
- 资源卡片列表
- 当前画像摘要

## 6. 详细实施顺序与阶段验收标准

### 6.1 第 1 阶段：打通聊天主链路
**实施顺序**
1. 稳定会话、消息、资源持久化
2. 固化 SSE 事件协议
3. 接入最小 Wiki 检索与最小画像基线
4. 清理并稳定 Router → Planner → Doc / Quiz / Code 链路
5. 完成聊天页、流式消息、资源卡片、Agent 状态

**验收标准**
- 可通过 `/api/chat/session` 创建会话，并在同一会话内连续发送至少 3 轮消息
- `/api/chat/stream` 成功响应时，SSE 事件序列至少包含 `agent_status`、`token`、`resource_card`、`done`
- 针对同一主题请求，系统稳定返回 3 类资源：`document`、`quiz`、`code`
- 每类资源都能在数据库中查询到对应记录，并能在前端按资源卡片渲染
- 当 Wiki 检索成功时，生成内容不为空；当 Wiki 检索失败时，前端可看到明确中文提示而不是静默失败
- 页面刷新后，用户能重新看到该会话的历史消息与已生成资源

### 6.2 第 2 阶段：接入 Wiki / RAG / 画像
**实施顺序**
1. 跑通常识库完整导入与向量索引
2. 补齐基础 BM25 / 向量混合检索与引用组织
3. 让 Doc / Quiz / Code / Tutor 生成前强制检索 Wiki
4. 补齐知识图谱 / DAG 基础查询能力
5. 完成 ProfileAgent 的画像提取、持久化与摘要读取
6. 前端完成画像页与引用展示

**验收标准**
- 知识库导入命令可成功执行，且能查询到演示主题对应的知识条目
- Doc / Quiz / Code / Tutor 的生成请求在正常路径下都会先经过 Wiki 检索
- 生成结果中能稳定返回来源章节或来源条目，并在前端可见
- 连续对话后，画像记录可持久化更新，画像页能展示最新摘要
- 知识图谱 / DAG 查询接口可返回路径规划所需的前置 / 后继关系
- Wiki 检索异常时，接口返回明确中文错误提示或受控降级结果

### 6.3 第 3 阶段：比赛演示版闭环
**实施顺序**
1. 实现学习路径 API 与路径页
2. 接入 TutorAgent
3. 实现资源中心与资源详情页
4. 实现 Wiki 浏览页
5. 优化聊天页 Agent 状态与资源组织方式
6. 补齐演示脚本对应的空态、异常态和中文文案

**验收标准**
- 能按固定演示脚本完整走通“提问 → 资源生成 → 保存资源 → 看画像 → 看路径 → 继续答疑”流程
- Tutor 成功回答时，SSE 流正常结束，且回答文本带有知识依据或来源提示
- 路径页能基于画像摘要、主题目标与 DAG 关系返回至少一条可展示学习路径
- 资源中心能查看资源列表与至少一种资源详情页
- Wiki 页能完成知识条目列表、检索与详情浏览
- 所有页面关键文案、按钮、空态、错误提示均为中文

### 6.4 第 4 阶段：增强与打磨
**实施顺序**
1. MediaAgent 或最小多媒体能力
2. 内容审核与输出过滤
3. 缓存与性能优化
4. 错误恢复与更完整日志
5. Demo 细节打磨

**验收标准**
- 新增强项接入后，不破坏前 3 阶段既有接口与演示主链路
- 至少一个增强能力可独立演示且结果可见
- 部分依赖失败时，系统仍能返回受控错误或降级结果，而不是整体不可用
- 日志中可定位主要失败阶段，便于现场排查

## 7. 风险点与关键决策

### 7.1 主要风险点

#### 前端基础较薄
当前前端离比赛演示所需的聊天流式体验、资源卡片、画像页、路径页、Wiki 页仍有较大差距。

**影响**
若不控制顺序，容易出现后端做了很多但前端展示跟不上的情况。

#### Orchestrator 易膨胀
当前 Orchestrator 已承担路由执行、画像更新、资源生成、token 拆分、资源落库与事件输出。MVP 尚可接受，但继续加入 Path / Tutor / Media 后会迅速变重。

**决策**
后续实现中必须控制它只做“编排 + 事件流”，把持久化与查询逐步下沉到 service。

#### Wiki 真实集成是关键路径
由于采用真实集成优先，知识导入、向量化、检索和 Agent 使用检索结果生成不能只留接口。

**决策**
Phase 1 先打通最小知识导入与生成前检索，Phase 2 再补齐完整 RAG、引用组织与知识图谱 / DAG 能力。

#### 比赛演示版目标较大
首个可交付版本已经覆盖对话、画像、资源生成、路径、Tutor、Wiki、资源中心，范围很大。

**决策**
首版强调“闭环真实可演示”，工程增强项统一延后。

### 7.2 比赛演示版运行前提与降级策略

#### 运行前提
比赛演示版要稳定运行，至少需要满足以下前提：
- 后端服务、前端服务、数据库与知识库初始化脚本可一次性启动
- 初始知识库已完成导入，且至少覆盖演示主题所需章节
- 演示账号、演示会话与基础种子数据可提前准备
- Demo 使用的 LLM / 向量检索依赖在现场环境可访问
- 页面核心文案、空态文案、异常提示全部为中文

#### 降级策略
若现场环境不稳定，允许按以下顺序降级，但不得破坏主链路可见性：
1. 优先保留聊天、SSE、3 类资源生成、基础 Wiki 引用展示
2. 学习路径首版可退化为规则 + DAG 结果展示，不依赖复杂优化策略
3. Tutor 优先保留基于当前会话资源与 Wiki 的问答，不接入复杂教学状态机
4. Wiki 页优先保留浏览、检索、详情，不做编辑后台
5. MediaAgent、审核、缓存、自动恢复等增强项全部后置

比赛现场外部依赖失效时的产品内边界进一步固定为：
- 若外部 LLM 不可达：停止新的实时资源生成、Tutor 实时答疑与路径实时生成；前端显示中文受控提示；允许演示已生成资源、Wiki 浏览、画像页与预置会话回放
- 若向量检索不可用但 Wiki 条目数据仍可读：停止“带知识依据”的正式生成链路；允许演示 Wiki 浏览、资源详情查看与预置结果展示，不把无检索生成结果冒充为知识支撑结果
- 若知识库初始化失败：不进入正式实时演示流程，改为预置会话、预置资源与只读页面演示模式，并在演示脚本中提前标注这是降级模式
- 人工兜底只用于解释当前处于哪种降级模式与引导切换页面，不替代产品内本应由系统完成的生成结果

#### 非代码交付物
除代码外，比赛演示版还应同步准备：
- 一页式演示脚本，明确演示顺序与每一步预期结果
- 演示环境启动说明
- 初始知识库内容清单
- 关键异常场景下的人工兜底话术
- 预置会话、预置资源与只读演示页面清单
本次设计已经确定：
1. 先拆路线图，再从 Phase 1 开始
2. 总体策略是折中方案
3. 前后端一起推进
4. 真实集成优先
5. 首个可交付版本是比赛演示版
6. 工程增强项延后

这些决策构成后续实施计划的前提，不建议在进入实现后再频繁摇摆。

## 8. 最终建议结论

建议后续实现严格按如下主线推进：

1. 先完成聊天主链路和 3 类资源生成
2. 再接 Wiki / RAG 与画像
3. 再补路径、Tutor、资源中心、Wiki 页面
4. 最后再做 Media、审核、缓存、恢复、性能

总原则是：

> 先让一条链路完整可见，再扩下一条链路。

即：
- 不先做完所有后端再碰前端
- 不先把所有页面空壳铺满
- 不先把所有 Agent 名义建完却没有真实联动

而是确保每个阶段都能给用户带来可见价值，并逐步构成比赛演示版所需的完整闭环。
