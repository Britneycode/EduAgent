# EduAgent 全面工程体检与中等规模优化设计

日期：2026-04-18
主题：对 EduAgent 项目进行全面工程体检，并在可控范围内直接修复高确定性问题

## 1. 背景与目标

当前 EduAgent 仓库已经具备前后端骨架、Agent 架构设计与部分页面/接口实现，但从已有提交状态与项目文档看，仓库仍处于快速迭代阶段，可能同时存在以下几类问题：

- 前后端静态检查、类型检查、构建链路中的显性错误
- 关键页面与核心服务中的明显实现缺陷
- 代码结构重复、边界不清、可维护性不足的问题
- 与项目既有约束不一致的实现，例如中文 UI、暖色设计约束、服务分层约束等

本次任务目标不是做一次大规模重构，而是执行一次“全面工程体检 + 中等规模优化”，以较高性价比提升当前仓库的可运行性、稳定性和工程质量。

本次已确认的工作方式：

1. 审查范围采用全面工程体检，而不是只看单点 bug
2. 审查后直接修改我能确认正确的问题
3. 修改范围控制在中等规模，不做大重构
4. 结束标准为尽量多修，并附带剩余问题清单

## 2. 推荐执行方案

本次可选路径有三种：

### 方案 A：分层体检 + 选择性修复（推荐）
先运行现有检查链路，再结合代码阅读与关键路径抽查，按高确定性原则直接修复问题。

执行顺序：
- 运行前后端 lint / type-check / build / 测试等现有命令
- 阅读关键模块代码并定位高价值问题
- 分批修复可明确判断正确的问题
- 每批修复后重新执行相关检查
- 最终汇总已修复项、未修复项与后续建议

**优点**
- 覆盖面广，能同时发现构建、类型、静态质量和结构问题
- 适合当前“全面体检 + 直接修改”的目标
- 可在有限改动下产出较稳定的收益

**缺点**
- 对深层业务正确性的覆盖不如专项业务审计
- 仍需人工判断哪些问题适合本轮直接修复

### 方案 B：代码阅读主导的结构治理
以阅读代码为主，优先发现架构、职责分配、重复实现、可维护性问题，再挑选部分修复。

**优点**
- 更容易发现设计层问题
- 对长期维护质量更有帮助

**缺点**
- 容易漏掉类型错误、构建失败和运行时显性问题
- 对“尽量多修”目标不够直接

### 方案 C：用户路径主导的端到端检查
围绕聊天、画像、Wiki 等真实用户路径做端到端检查，并按使用流程修复问题。

**优点**
- 更贴近实际体验
- 更容易发现交互断点

**缺点**
- 对全仓工程质量覆盖不足
- 容易漏掉未被路径触达的代码质量问题

### 方案结论

推荐采用 **方案 A：分层体检 + 选择性修复**，并将重点放在：

- 前端：chat / profile / wiki 主路径及其共享组件
- 后端：api / services / agents / wiki 核心模块
- 工程链路：lint、type-check、build、测试、关键依赖和目录结构一致性

## 3. 执行范围与边界

### 3.1 本次纳入范围

1. 前端工程质量检查
   - ESLint
   - TypeScript 类型检查
   - Next.js 构建
   - chat / profile / wiki 核心页面与共享组件抽查

2. 后端工程质量检查
   - pytest
   - ruff check / format 相关问题识别
   - API、service、agent、wiki 模块代码阅读

3. 可控范围内的直接修复
   - 明显 bug
   - 构建失败、类型错误、静态检查错误
   - 低到中风险的结构优化
   - 明显违反项目约束的前端文案/实现问题

### 3.2 本次不纳入范围

1. 大规模架构重写
2. 业务规则不明确但需要产品决策的问题
3. 大面积样式重做或整站视觉翻新
4. 引入新的大型基础设施或重度依赖迁移
5. 需要真实外部服务联调才能确认正确性的深层改造

### 3.3 修改准入标准

只有同时满足以下条件的问题，才在本轮直接修改：

- 我能明确证明问题存在
- 我能较高把握地判断修复方案正确
- 修改范围局部可控，不会引入大面积连锁风险
- 修改后能用检查命令、代码路径复核或局部验证进行确认

不满足上述条件的问题，将进入“剩余问题清单”，只说明现象、影响和建议方向，不贸然改动。

## 4. 详细执行流程

### 阶段 1：基线检查

目标：快速建立仓库当前健康状态，识别显性失败点。

执行内容：
- 查看前后端可执行检查命令与依赖状态
- 运行前端 lint / type-check / build
- 运行后端 ruff / pytest
- 记录失败信息、警告类型和问题聚类

产出：
- 一份问题基线：哪些命令失败、失败集中在哪些模块、是否存在环境性阻塞

### 阶段 2：关键代码阅读与问题归类

目标：结合项目架构与文档，对高价值区域做有针对性的代码审查。

重点区域：
- 前端 chat 页面相关组件与状态流
- Session / Sidebar / Message / Resource Card 等交互组件
- profile / wiki 页面及其数据获取逻辑
- backend/app/api/、services/、agents/、wiki/ 下核心实现

问题分类方式：
- P0：阻断运行 / 构建 / 类型 / 明显错误
- P1：关键路径体验问题、错误边界、数据流缺陷
- P2：重复代码、职责混杂、命名/结构不清、可维护性问题
- P3：建议项，不适合本轮直接动手

### 阶段 3：分批修复

目标：按收益与确定性优先级逐批处理问题。

处理顺序：
1. P0：构建、类型、lint、测试阻断项
2. P1：chat / profile / wiki 主路径中的明显缺陷
3. P2：局部结构优化、重复逻辑收敛、易维护性改进

修复原则：
- 小步提交思维，但本轮不强制拆成多个提交
- 不为未来假设做抽象
- 优先沿用现有模式，避免平地起新范式
- 前端所有用户可见文案保持中文
- 不添加无必要注释

### 阶段 4：回归验证

目标：验证修复确实解决问题，且未引入明显回归。

执行内容：
- 重新运行受影响的 lint / type-check / build / pytest / ruff
- 对改动涉及的关键代码路径进行人工复核
- 如果前端涉及可交互页面，尝试启动并验证关键路径；若因环境受限无法完成，明确说明

### 阶段 5：结果汇总

目标：形成可交付的审查与优化结果。

最终输出分为三类：

1. **已修复并验证的问题**
   - 包括问题现象、修改位置、验证方式

2. **发现但暂未直接修复的问题**
   - 包括原因：需要更多上下文、风险偏高、依赖外部环境、需要产品判断等

3. **后续建议清单**
   - 包括建议优先级与可选后续动作

## 5. 风险控制与决策规则

### 5.1 风险控制

为了避免“全面检查”演变成失控重构，本次采用以下边界：

- 不为顺手而做与目标无关的清理
- 不对不熟悉的业务逻辑做推测性改写
- 不因为发现风格问题就大面积统一重构
- 若某问题可能影响大量调用方，则优先记录而不是直接改

### 5.2 决策规则

当遇到问题时，按以下顺序决策：

1. 这是否会导致命令失败、页面报错、明显错误结果？
2. 这是否位于 chat / profile / wiki 主路径？
3. 是否能在局部安全修复？
4. 修复后是否可以明确验证？

只有前两项价值高、后两项答案为“是”的问题，才优先进入本轮修改。

## 6. 验收标准

本次任务完成的标准为：

1. 已对前后端主要检查链路执行过实际检查
2. 已修复一批高确定性、高价值问题
3. 已对修复结果执行相应复核或命令验证
4. 已输出剩余问题清单，说明暂不修改的原因
5. 若存在环境限制，已明确说明哪些验证无法完成

这意味着本次工作的目标不是“仓库完全无瑕疵”，而是让当前仓库在有限时间内达到“更健康、更可运行、更易继续开发”的状态。
